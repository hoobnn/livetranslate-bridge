# 网络、模型调用与上行音频优化（2026-09-28）

## 先做的协议实测

直连 `qwen3.8-livetranslate-flash-realtime`（北京），用 `samples/downlink.wav` 作输入：

| 问题 | 结果 | 对实现的影响 |
|---|---|---|
| WebSocket ping | 服务端回 pong，往返 50–80 ms | 可以用 ping 判断连接是否存活，不必只靠“40 秒没收到消息” |
| 建连耗时 | `resume()` → `session.created` 0.16–0.22 s，再到 `session.updated` 约 0.07–0.09 s | 一次重连约 0.3 s，加上首次退避 0.25 s |
| 会话中途再发 `session.update` | 被拒绝：`invalid_value` “session already started or finished or failed”，随后断开 | 输出模态、术语表都只能在建连时定；要改只能重开会话 |
| 停发音频 2 分钟 | 会话不关闭，期间没有服务端事件，ping 全部有回应；恢复发送后在同一会话里正常识别和翻译 | 静音时可以停止上传；此时“收不到消息”不能再当作断线 |
| 官方文档 | `speaker_detection` 的阈值固定为 0.5；ASR 无法关闭且免费；翻译无法关闭；`translation.corpus.phrases` 可用 | 两侧没法分别调断句阈值；转录模式不值得为了省翻译费用换模型（文字输出费用很低） |

音色模式的延迟：用 `scripts/replay-translation.sh samples/downlink.wav … audio <mode>` 每种模式跑 2 轮，每种各得到 4 个响应：

| 模式 | 从开始说话到第一块译声（中位数） | 译声比译文文字晚到（中位数） |
|---|---:|---:|
| 普通音色 | 1.52 s | 0.18 s |
| `once` | 1.66 s | 0.20 s |
| `always` | 1.66 s | 0.21 s |

复刻音色比普通音色慢约 0.15 s，但 `always` 并不比 `once` 慢，所以对方一侧保留每次回复都复刻（`always`）。样本很小，只能当作量级参考。

计费（北京，原价）：音频输入 40 元/百万 token，文字输出 100 元/百万 token，音频输出 160 元/百万 token。成本主要来自上传的音频时长和合成的译声。

## 改动

**网络（`TranslationClient`）**
- 整个 client 只用一个 `URLSession`，`close()` 时调用 `invalidateAndCancel()`。原来每次重连都新建一个 session 且从不作废，会泄漏。
- 每 5 s 发一次 ping，9 s 没收到 pong 就重连。
- 用 `NWPathMonitor` 监听网卡变化，系统唤醒时也会触发，两种情况都立即重连，并重置退避。只比较主网卡，因为 `awdl0`（AirDrop）和 `utun*`（VPN、专用代理）会随时出现和消失，但它们不代表到服务端的线路变了。
- `networkServiceType = .responsiveData`，`waitsForConnectivity = false`。
- “40 s 没收到消息”这项检查只在最近 10 s 内发过音频时才启用。
- 休眠：连续 10 s 没发音频时，如果连接断了就先不重连；等音频恢复再立即重开（不走退避）。补发缓冲把这段音频带过握手。
- 补发缓冲和发送队列的上限都从 1 s 调到 2 s，两者保持一致，避免重连后补发的音频在发送队列里被裁掉。
- 音频消息直接拼 JSON 字符串；`CALLAUDIO_DEBUG` 只读一次，不再每收一帧都读环境变量。

**上行音频（`AudioPath`、`SilenceGate`）**
- 采集到的约 10 ms 小块先攒成 40 ms 再发，每个方向每秒约 94 条消息降到 25 条，最多多等 30 ms。
- 对方一侧始终启用静音门控：检测的是“数字静音”（峰值 ≤ 8），持续 3 s 后停发；一出声立即恢复，并补发之前 0.5 s 的音频。3 s 的持续时长长于服务端 2.5 s 的句末静音，不会影响断句。
- 麦克风一侧的门控作为可选设置，默认关闭：低于 −50 dBFS 持续 3 s 后停发。

**模型调用（`SubtitleModel`）**
- 术语表：在设置里每行填一条“原词 = 译词”，两个方向共用，写入 `translation.corpus.phrases`。真实调用中 `hello = 哈喽` 生效了。
- 开始会话时，如果某一侧的译声音量为 0，这一侧只请求文字，不再为听不到的语音付费。之后把音量调高到 0 以上，停手 0.8 s 后会用保留字幕的方式重开会话，重新请求语音。
- 删除 qwen3.8 已经不用的 `Segmentation`（静音时长、VAD 阈值），以及它的偏好和文案。

**译声播放（`TranslationPlayer`）**
- 译声通道加了 `AVAudioUnitTimePitch`：积压超过 3 s 时以 1.15× 播放，超过 6 s 时 1.3×，降到 1.5 s 以下恢复 1×，音调不变。1× 时绕过该节点。每次切换绕过状态，节点内部缓冲的约 100 ms 语音会被丢掉；有滞后区间，所以切换不频繁，但能听出来。原来积压到 15 s 就丢弃的规则保留，作为最后兜底。

## 验证

- 单元测试 136 项通过、0 失败。新增：静音门控（何时停发、预录顺序、峰值边界）、术语表的解析与写入、偏好持久化、积压时加速和恢复。
- 用生产代码的 `TranslationClient` 做真实调用：
  - 停发 25 s 后没有重连，恢复后在原会话里继续出译文；
  - 停发期间模拟断线，client 进入休眠不重连；音频恢复后 0.19 s 建立新会话，0.33 s 就绪，句首没丢。
- 尚未实测：
  - 真实通话中切换 Wi-Fi、睡眠唤醒后的重连；
  - 麦克风门控在不同麦克风上的误判率；
  - 加速播放的主观听感；
  - 帧合并对首条译文延迟的影响（没有做对照，预期不超过 30 ms）。

## 没做的

- **回声消除**：原因见 `audio-capture-2026-09-23.md`，仍需单独做实机验证。
- **转录模式换用专门的 ASR 模型**：qwen3.8 的识别免费，翻译的文字输出费用很低，换模型的收益抵不过另接一套协议的成本。
- **两侧分别调断句阈值**：qwen3.8 的 `speaker_detection` 阈值固定为 0.5，没有可调空间。

## 输入输出链路核查

用一个硬件回环测试程序直接编译生产代码 `CallAudioKit`：`TranslationPlayer` 往 BlackHole 2ch 播放已知正弦音，`UplinkCapture` 从 BlackHole 读回，经过 `RealtimeAudioQueue` 和 `Resampler` 得到 16 kHz PCM。每 10 ms 一个窗口拟合正弦，检查电平、频率和残差（用来发现断点和爆音）。

**修复的两个问题**

| 问题 | 现象 | 修复 |
|---|---|---|
| `UplinkCapture` 用 `inputNode.outputFormat(forBus:)` 作为连接格式 | 切换到非默认设备后，这个格式仍然是默认麦克风的（1 声道），AUHAL 于是只送第 1 声道。实测：只在 BlackHole 右声道放音时，识别端完全静音 | 改用 `inputFormat(forBus:)`，它反映的是切换后设备的硬件格式 |
| `RealtimeAudioQueue` 遇到超过 2 声道的输入 | `AVAudioFormat(commonFormat:…channels:)` 在 3 声道及以上时返回 nil，采集数据被静默丢弃，也没有计入丢帧；即使改用离散声道布局，`AVAudioConverter` 也只会输出静音 | 3 声道及以上折叠为单声道（各声道相加后限幅），任意一路上的麦克风都能以原电平通过；构造失败时计入丢帧 |

**实测结果（修复后）**

| 链路 | 结果 |
|---|---|
| 译声（24 kHz）→ BlackHole → 采集 → 16 kHz | 电平 0.500（输入 0.5），所有 10 ms 窗口都没有断点，队列没有丢帧 |
| 原声（48 kHz 单声道，每块 10.7 ms）→ 立体声输出 → 采集 | 电平 0.500，没有断点 |
| 只在右声道放音 → 采集 | 电平 0.25（立体声按平均下混，符合预期；修复前为 0） |
| 输出到 4 声道聚合设备（BlackHole + Oray） | 前两路输出正确，没有断点 |
| 积压 8 s 译声 | 6.5 s 播完，音调不变，最大残差 2.6% |
| QuickTime → tap（接管源应用） | 频率准确，没有断点。电平与 QuickTime 实际送到设备的完全一致（立体声源 0.353，单声道源 0.5），接管前后音量一致 |
| 整个 App，下行方向（QuickTime 英文语音 → BlackHole 输出） | 字幕逐字正确，译文正确；从输出设备录回的声音里，识别到了英文原声和中文译声 |
| 整个 App，上行方向（BlackHole 作为麦克风，中文语音） | “我”这一侧的字幕和英文译文正确 |

## 支持聚合设备作为麦克风

**采集方式**：`UplinkCapture` 从 `AVAudioEngine` 改为直接在输入设备上挂 HAL IOProc，和 `DownlinkTap` 的做法一致。
- `AVAudioEngine` 的输入节点只暴露设备的第一个流，聚合设备里第二个及以后的成员都采不到。
- IOProc 按设备自身的布局拿到全部流（每个流一个缓冲，缓冲内交错多个声道），运行在实时线程上，按设备的 IO 缓冲大小回调。
- 同一台设备上可以同时挂多个 IOProc，不像两个 engine 那样争抢 AUHAL。
- 对双工设备，本 IOProc 在输出流上的处理会被关闭。

**配套改动**
- `CapturedAudio` 按每个缓冲的 `mNumberChannels` 通用处理；`RealtimeAudioQueue` 的槽位统一改为逐声道存放。
- 3 声道及以上折叠为单声道时，按“活跃声道”取平均，增益在块内线性过渡：
  - 麦克风只接在一路上时保持原电平；
  - 同一段内容出现在两路上时不会叠加成削波（原来直接相加，实测 0.5 + 0.5 = 1.0）。
- 活跃判定带滞回：峰值超过 −50 dBFS 才进入活跃，连续 0.5 s 没超过才退出。闲置输入的底噪如果在单一阈值附近，会逐块进出活跃状态，给人声带来 6 dB 的颤动。单元测试用 −58 dBFS 的底噪验证过这一点，旧的 −60 dBFS 固定阈值会让人声电平减半。代价是：两路都在说话时，一路停下后，另一路会有 0.5 s 维持在平均后的电平。
- 路由快照改为比较所有流的声道总数（原来只看第一个流），聚合设备的成员变化会触发会话重建。上行采集不再固定声道数，重建完成之前的这段时间，音频按新的布局照常送出。
- 输入、输出设备都会读出聚合设备的成员：
  - 任一成员是回环设备，整个设备就视为回环；
  - 防回灌检查改为比较“输入端的回环 UID”和“所有输出所到达的 UID”（包括多输出设备的成员），有交集就拒绝启动。
- 麦克风列表不再出现 App 自己为 tap 建的私有聚合设备。

**实测**
- 测试程序：私有聚合设备 [Oray, BlackHole]，BlackHole 位于第二个流：

| 情况 | 结果 |
|---|---|
| 聚合设备 4 声道，BlackHole 两路同一内容 | 电平 0.500，没有断点、没有丢帧 |
| 聚合设备，只在 BlackHole 右声道放音 | 0.500 |
| 普通 BlackHole 2ch | 0.500；只在右声道放音时为 0.25 |
| 默认输入（内置麦克风） | 正常采集，没有丢帧 |

- 整个 App：用公开聚合设备（Oray + BlackHole）作为麦克风：
  - “对方听到的声音”也选 BlackHole 时，App 拒绝启动并提示回灌风险；
  - 去掉本地输出后正常运行，“我”这一侧字幕和译文正确。
